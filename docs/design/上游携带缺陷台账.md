## 1. 断链符号链接让 `statSync` 抛 `ENOENT`

- **现象**：`sortedDirs()` 的过滤链是 `existsSync(父目录)` → `readdirSync` → `join` → `statSync(full).isDirectory()`。`existsSync` 只挡住了「父目录不存在」，`readdirSync` 会把断链符号链接**当成普通目录项列出来**，随后 `statSync` 跟随链接、目标不存在，直接抛错。整个 `validateComparisonWorkspace()` 因此抛出异常，而不是返回 `{ valid: false, issues: [...] }`。
- **触发条件**：工作区（或其 `runs/` 目录）下存在任意名字的**断链**符号链接（`mklink` 后目标被删、检出时链接未展开、跨机器拷贝断链等）；不限于 `eval-*`、`run-*` 命名——名字过滤发生在 `statSync` 之后。
- **影响**：守卫的契约是「返回问题清单」，实际却可能抛错。调用方若没包 `try/catch`，用户看到的是 `ENOENT: no such file or directory, stat '...'` 这种与「评测目录不完整」无关的底层错误，无法据此修复；上游入口处也未捕获该异常。
- **当前处置**：**已修（2026-10-30）**。`sortedDirs()` 改为逐项 `lstat` 判定（不跟随链接），符号链接 / junction 再 `stat` 解析目标；不可解析项**跳过**并往 `issues` 追加一条 `目录项不可解析，已跳过：<名字>（<错误码>）`，守卫回到「返回问题清单」的契约。父目录本身不可解析时按「无子目录」返回，不再抛错。
- **修复建议**（已落地）：`lstatSync` 判目录项 + `try/catch` 跳过不可解析项，跳过原因进 `issues`，不静默忽略。
- **修复后要改的用例**（已改）：`test/lib-workflow-guard.test.js` 的「断链符号链接被跳过并作为一条 issue 返回，不再让整个守卫抛错」——断言 `valid === false`、`evalCount === 0`，且恰好一条 `evalDir` 为该链接名的 issue 同时含「不可解析」「已跳过」，并列断言「缺评测目录」的原有 issue 仍在。
- **残留**：断链项与「缺 `eval-*` 目录」会同时成条（前者是原因、后者是结果），这是有意保留的信息叠加，不是重复报错。

## 2. 空 `outputs/` 目录也算「有运行」

- **现象**：`hasAtLeastOneRun()` 在没有 `run-*` 目录时，只要 `outputs/` **存在且是目录**就返回 `true`，不检查其中是否有任何产物文件。
- **触发条件**：评测跑挂或中途清理，留下空的 `with_skill/outputs/` 或 `without_skill/outputs/`。
- **影响**：守卫放行一个实际没有产物的评测目录，评审查看器打开后是空的。属于「少报问题」，不影响数据正确性，故记为低。
- **当前处置**：**已修（2026-10-30）**。`hasAtLeastOneRun()` 在 `outputs/` 是目录的基础上再要求 `readdirSync(outputs).length > 0`；空目录、不可读目录、断链链接一律按「无运行」计，由既有的「缺运行产物」issue 报出（不新增重复条目）。
- **修复建议**（已落地）：`outputs/` 至少一个条目才算有运行。
- **修复后要改的用例**（已改）：原「只有 outputs 目录也算有过运行产物」拆成两条——「空 outputs 目录不算有运行产物，缺运行的问题照常报出」（断言 `valid === false` 且两条缺运行 issue 齐全）与「outputs 目录里有产物时算有运行产物」（断言 `valid === true`、`issues === []`）。

## 3. `JSON.parse` 结果不校验数组，存成 `{}` 会在排序处抛 `TypeError`

- **现象**：`readStore()` 用 `JSON.parse(...) as GoldStandard[]` 断言类型，运行时**不校验**结构。存储文件内容是合法 JSON 但不是数组（如 `{}`、`null`、`{"a":1}`）时，`readStore` 正常返回，随后 `sortStandards()` 的 `[...standards].sort(...)` 抛 `TypeError: standards is not iterable`。
- **触发条件**：存储文件被手工编辑成对象、被别的工具写坏、或 `JSON.stringify` 写入了非数组根（上游只由自身写入，正常路径不会产生；属于外部篡改/损坏场景）。
- **影响**：错误是**远离出错点**的 `TypeError`，既没有存储路径也没有「malformed」字样，与同类场景（`SyntaxError` → 带路径的 `Failed to read gold standards store at ...: malformed JSON`）体验不一致，用户无从定位是哪份文件坏了。
- **当前处置**：**已修（2026-10-30）**。`readStore()` 在 `JSON.parse` 后做 `Array.isArray` 校验（`... : expected a JSON array, got object / null / ...`），再逐条校验必需字段（`id`/`createdAt`/`skillName`/`description` 必须是字符串、`passRate` 必须是有限数、`notes` 若存在必须是字符串），失败时抛 `... : invalid record at index <n> (...)`。两种错误都带完整存储路径，与 malformed JSON 分支同款口径。
- **修复建议**（已落地）：解析处即校验结构，错误带路径。
- **修复后要改的用例**（已改）：原「存储内容是对象时排序处抛 TypeError」改为 `test/lib-gold-standards.test.js` 的「存储不是数组或记录缺必需字段时抛带存储路径的结构错误」：`{}`、`null`、`[{ "id": "only-id" }]` 三个子场景，各对 `listGoldStandards` 与 `getGoldAdvice` 两个入口断言「不是 `TypeError`、message 以带存储路径的前缀开头、命中对应结构错误文案」。
- **残留**：字段校验只做「必需字段存在且类型正确」，不校验 `passRate` 是否在 0～1（那由写入侧 `addGoldStandard` 把关；读侧放宽是为了不把历史数据判死）。

## 4. 只认小写开头键，`Allowed-tools:` 被静默忽略

- **现象**：键值匹配正则 `^([a-z][a-z0-9_-]*)\s*:\s*(.*)$`（修复前位于 `src/lib/validate.ts`，现只保留在 `src/cli/validate.ts:135`）要求首字符为小写字母；`Allowed-tools:` 这类大写开头的键不匹配，落到「嵌套键」分支（`^\s+\w+\s*:`，要求前导空白）也不匹配，于是**既不进 `frontmatter`，也不进 unexpected-key 列表**。该行被完全丢弃，校验继续跑并可能返回「技能校验通过」。
- **触发条件**：frontmatter 出现任何大写开头（或数字、其他字符开头）的顶层键，最典型的是把 `allowed-tools` 拼成 `Allowed-tools`。
- **影响**：拼错的键被静默吞掉，用户在 YAML 语义上写了但运行时拿不到（例如工具白名单失效），而校验器仍报通过——属于「假通过」，比报错更危险，故记为中。
- **当前处置**：**已修（2026-10-30）**。顶层键探测改为宽松正则 `^([^\s:#][^:]*?)\s*:\s*(.*)$`（前导空白仍归嵌套键分支），收集完再按 `^[a-z][a-z0-9_-]*$` 严格判定键名：不合规键报 `frontmatter 含不合规的顶层键：Allowed-tools（应写作 allowed-tools）…`，在「未知键」判定**之前**返回，避免被后续字段校验掩盖。CLI 的 `validate` 子命令经 `collectIssues` 里的 `validateSkill` 兜底，同步从「通过」变为报错（`src/cli/validate.ts:309`）。
- **修复建议**（已落地）：宽松顶层键探测 + 键名严格判定并给写法建议，不丢弃该行。
- **修复后要改的用例**（已改）：`test/lib-validate.test.js` 的「钉住上游缺口：大写开头键被静默忽略」改为「大写开头的顶层键报错并给出正确写法」（断言 `valid === false`、message 含「不合规的顶层键」、含 `Allowed-tools`、含「应写作 allowed-tools」）；另加配对用例「大小写正确的 allowed-tools 键仍然通过」，防止修复变成「合法键也判错」。
- **残留**：CLI 逐条扫描（`src/cli/validate.ts:135`）仍用小写正则，因此该错误经兜底以「校验未通过：…」一条呈现、不带行号；要带行号需同批改 CLI 扫描，属独立批次。→ **已由第 7 条修复（2026-10-30）**。

## 5. `history` 为空时求最佳迭代的 `reduce` 抛 `TypeError`

- **现象**：`generateHtml()` 用两处 `history.reduce(...)` 求「高亮那一行」的最佳迭代，**没有初值**。`history` 为 `[]`、`null` 或缺失时（`d.history ?? []` 后仍是空数组），`reduce` 直接抛 `TypeError: Reduce of empty array with no initial value`，整个报告生成崩溃，一份 HTML 都产不出来。
- **触发条件**：任何「还没有任何一次迭代」的调用——直接以空数据调用 `generateHtml`，或 optimize 流程在第一轮迭代落盘前就请求实时报告。
- **影响**：空数据是最常见的起始状态（刚启动优化、历史文件被清空、上游写入失败），崩溃点是纯渲染层，用户既看不到报告也读不到有用错误；`run-loop` 的实时报告路径同样受影响（`src/lib/run-loop.ts:366`）。
- **当前处置**：**已修（2026-10-30）**。求最佳迭代前先判 `history.length > 0`，空数据不进 `reduce`（`bestIter` 保持 `undefined`），渲染成一份**只有表头、没有数据行**的空报告，概要各行按缺省值（`无` / `0` / `?`）渲染。`generateHtml` 的 JSDoc 同步删掉旧的 `@throws TypeError` 说明。
- **修复建议**（已落地）：空历史渲染空报告，不抛错。
- **修复后要改的用例**（已改）：原「钉住上游缺口：history 为空数组时在求最佳迭代处抛 TypeError」改为 `test/lib-report.test.js` 的「history 为空数组 / null / 缺省时渲染空报告而不抛错」：`{}`、`{ history: [] }`、`{ history: null }` 三个子场景，断言不抛错、产出的 HTML 完整（含 `</html>`）、无 `<tr class="` 数据行、概要行不含 `undefined`。

## 6. `aggregate` 里的第二份 `sortedDirs`：断链链接与同名文件让汇总抛错

- **现象**：`src/lib/aggregate.ts:234` 有**第二份** `sortedDirs()`（与 `workflow-guard` 的实现同源但各写一份），目录项判定用 `statSync(full).isDirectory()`（跟随链接），父目录只过了 `existsSync(dir)` 就直接 `readdirSync(dir)`。因此两类输入会让 `loadRunResults()` 抛错：① 断链符号链接 / junction ⇒ `statSync` 抛 `ENOENT`；② 占位的**普通文件**（例如名为 `runs` 的文件，`loadRunResults:263` 用 `existsSync(runsDir)` 判布局，文件也算「存在」）⇒ `readdirSync` 抛 `ENOTDIR`。
- **触发条件**：benchmark 目录里有任意断链链接；或 `runs` 是同名文件；或 `eval-*` 位上是文件 / 断链链接。均属「检出未展开链接」「拷贝跨机器后断链」「手工留下同名文件」这类常见现场。
- **影响**：`aggregate` 汇总（CLI 的 `eval` 汇总也复用同一套统计）**整体中止**并抛出底层 `ENOENT` / `ENOTDIR`，与模块自己写明的「单个 `run-*` 目录有问题只警告并跳过，不中断整体汇总」（`loadRunResults` 的 JSDoc）自相矛盾；用户看到的是 Node 底层错误，无法据此判断该删哪个链接或文件。
- **当前处置**：**未修**（2026-10-30 复核时登记，本批只登记不修——不在该批需求卡范围内）。行为与上游一致，`aggregate.ts:227-228` 的注释也自认「断链符号链接会让本函数抛 `ENOENT`；该行为与上游一致，未修」。
- **修复建议**：与第 1 条同款——`lstat` 判目录项、符号链接再 `stat` 探目标，不可解析项跳过；父目录补 `statSync(dir).isDirectory()` 守卫，或把 `readdirSync` 包 `try/catch`。注意本模块**没有** `issues` 返回通道，跳过原因只能走 `console.error` 警告（与 `loadRunResults` 既有的「警告并跳过」口径一致），文案需单独定；不要照搬 `workflow-guard` 的「跳过项进 issues」形态。
- **修复后要改的用例**：`test/lib-aggregate.test.js` 需新增/改写——「`runs` 是同名文件、或目录里有断链链接时，汇总不中断、按跳过处理并输出一条警告」；同时补一条正例「指向目录的合法链接仍被当作配置目录」（对齐本批为 `workflow-guard` 补的正例，防止修成「链接一律跳过」）。

## 7. CLI 双套解析吞掉大写 frontmatter 键

- **现象**：第 4 条修的是 `src/lib/validate.ts`，但 CLI 的 `validate` 子命令还有**第二套逐行解析**（`src/cli/validate.ts:135`，修复前）：键扫描固定用 `^([a-z][a-z0-9_-]*)\s*:\s*(.*)$`，不匹配就 `return`（`:136`），`Allowed-tools:` 这类大写 / 数字开头的顶层键**整行被丢弃**——既不进键值表、也不报错。更麻烦的是兜底判据是 `!verdict.valid && issues.length === 0`（`:310`）：只要 CLI 已经报过**任何**一条问题，`validateSkill` 已识别出的「不合规键」就被整条丢弃。真机负例（目录名与 name 不一致 + description 1208 字符 + `Allowed-tools:`）因此只报出前两条，大写键完全不出现；只放大写键时虽能报出，但只有「校验未通过：…」一条笼统文案，没有行号。
- **触发条件**：frontmatter 出现大写 / 数字 / 其它非小写字母开头的顶层键，**且同时存在任意一条 CLI 能报的问题**（最常见的就是 name 与目录名不一致或 description 超长）。
- **影响**：`docs/tools.md` 承诺的「同一目录的多处问题一次报全」在真链路上不成立；用户修完看得见的两条再跑一次才可能发现第三条（甚至因为兜底被跳过而永远只看到笼统文案），无法按行定位。属于「少报 / 漏定位」，比误报更消耗排查轮次，故记为中。
