## 背景

评测的做法是：把被测技能的 `name` + `description` 合成为一份**新的技能目录**，放进一个**临时隔离根** `evalRoot`，再以 `evalRoot` 为工作目录跑 `opencode run`，看模型在一组 query 上有没有选中这份合成技能。命中率即触发率。

之所以必须隔离，是因为「不隔离就跑不动」：`opencode` 会从 `$PWD` 反解项目根并加载 project-scoped skills，如果沿用调用方的 `$PWD`，模型会加载**真实的那份被测技能**（原名），命中于是被记到真身身上，合成技能恒为 0 分（`.tmp/old/plugin/lib/run-eval.ts:800-807` 的注释写明了这一点）。所以 `cwd` 与 `PWD` 都必须钉到 `evalRoot`。

之所以还要**镜像**，是因为空目录同样不可信：`opencode` 的项目级配置（`.opencode/` 下的配置、根配置文档、`instructions` 引用的相对文件）真源都在源项目里，`evalRoot` 里没有就等于「裸环境评测」——模型面对的不是用户真实使用时的上下文，通过率与线上表现脱钩。

两者互相拉扯：镜像越多越接近真实环境，但镜像越多就越容易把**与被测对象无关的东西**（构建产物、无关目录、被测技能本体）一起搬进来。用户实测反馈集中在后一半：「评测时拷贝了多余的东西」「找 `.opencode` 向上找，结果用错了项目根」。下面 6 条据此整理，末尾给出镜像方案（**已定 C**）与对实现的约束 J1–J9。

## 机制图

源项目 → `evalRoot` 的镜像关系（`evalRoot = <系统临时目录>/opencode-skill-eval-<随机>`，`.tmp/old/plugin/lib/run-eval.ts:730`）：

```text
源项目根 projectRoot
├── .opencode/                       ──逐条目→  evalRoot/.opencode/          （跳过 skills/，:644-660）
│   ├── <其它配置项>                 ──逐条目→  evalRoot/.opencode/<同名>
│   ├── skills/                      ──不整体镜像；逐个条目处理（:662-690）
│   │   ├── <被测技能>               ──✗ 永不镜像（本体 + 祖先 + skills 根自身 + 指向它的别名）
│   │   ├── <兄弟技能 A>             ──逐条目→  evalRoot/.opencode/skills/<兄弟技能 A>
│   │   └── <兄弟技能 B>             ──逐条目→  evalRoot/.opencode/skills/<兄弟技能 B>
│   └── (指向 skills 的别名)         ──✗ 按 canonical 路径判掉（:656、:678、:687）
├── <根配置文档>                     ──→  evalRoot/<同名>                      （:603-606）
│   └── 其 instructions / {file:} 引用的相对文件  ──→ evalRoot/<相对路径>      （:608-629）
└── （其余一切：src/、dist/、node_modules/、.git/、测试数据 …）── 正常情况**不镜像**

合成技能（本次评测生成，非镜像）：
  evalRoot/.opencode/skills/<cleanName>/SKILL.md     cleanName = <技能名>-skill-<8位随机>  （:726-736）

不在镜像范围内、但仍在候选集里（坑 F）：
  全局技能 ~/.config/opencode/skills、~/.claude/skills、~/.agents/skills
    —— 不镜像，也不会被隔离（子进程继承 HOME / XDG_CONFIG_HOME，只覆盖 PWD，process.ts:48-50）
    —— 处理方式：在 evalRoot/.opencode/opencode.json 写 permission.skill.<基础名> = "deny"

运行：cwd = evalRoot，env = buildOpencodeEnv(evalRoot)（:800-807）
清理：finally 里 rmSync(evalRoot, { recursive: true, force: true })（:840-844）
搬运原语：linkOrCopyConfigEntry —— 先 symlinkSync，失败降级 cpSync(recursive)（:297-305）
```

一句话读法：**镜像的是「配置面」**（`.opencode/` 除 skills 的部分、根配置文档及其相对引用、兄弟技能），**不镜像的是「被测对象面」**（被测技能本体、其祖先目录、`skills` 根、指向 skills 的别名）。坑集中在三处：搬运原语的降级分支（A）、根路径怎么来（B）、以及**根本不在镜像范围内却照样可见的全局技能**（F）；两个面的边界判定对应 C/D，兄弟技能**必须进**（E，方案已定 C）。

## 六条坑

### A 整目录递归拷贝：symlink 失败就 `cpSync(recursive)`，无白名单、无大小上限

- **现象**：Windows 上跑评测，`evalRoot` 里凭空多出整个配置目录的内容，甚至几十 MB 的二进制、构建产物、`.git/`；评测变慢，磁盘占用飙高，临时目录删不掉（Windows 上文件被占用）。
- **根因**：`linkOrCopyConfigEntry`（`.tmp/old/plugin/lib/run-eval.ts:297-305`）先试 `symlinkSync`，`catch` 之后直接 `cpSync(source, target, { recursive: true })`。Windows 非开发者模式下创建符号链接常因权限失败（需要 `SeCreateSymbolicLinkPrivilege` 或开发者模式），于是**每一次镜像都走递归拷贝**；这条路径既没有条目白名单，也没有单文件/总大小上限，`readdirSync` 出来什么就拷什么。
- **后果**：拷贝体积与被镜像目录的**全部内容**成正比，而不是与「配置需要多少」成正比；被镜像进来的构建产物还会成为 `opencode` 的 workspace 内容（例如根配置文档里引用了 `dist/...`，镜像后路径真实存在，模型读到的就是构建产物），评测环境与预想不符；清理耗时与失败率同步上升。
- **正确做法**：**降级路径只能逐文件拷贝已知条目**——配置文档（白名单文件名）、配置文档明确引用的相对文件/目录、技能目录白名单（`SKILL.md`、`agents/**`、`references/**`、`templates/**`，与安装器共用同一份），其余条目**跳过**；同时给单文件大小设上限，超限跳过并记一条（调试开关下可见）。`symlinkSync` 成功时保持零拷贝（真实语义最接近）。**镜像方式固定为「逐条目 / 逐文件 + 单文件大小上限」**，禁止对任何目录调用 `cpSync(..., { recursive: true })`（含 `force` 兜底路径）；这条由源码 `grep` 门禁守住。
- **验收方式**：
  - 单测把 `symlinkSync` 打桩成抛 `EPERM`，源目录里放「白名单内 2 个文件 + 白名单外含 `node_modules/`、`dist/`、`.git/` 的目录 + 1 个超过上限的大文件」，断言 `evalRoot` 内文件集合 = 白名单/已知条目集合，且不含被跳过的任何路径；
  - 同一用例断言调试输出里列出「跳过的条目及其大小」。

### B `findProjectRoot`：无边界向上找，命中即返回，不校验、不报告

- **现象**：在子目录里跑评测（或在 monorepo 的子包里），镜像来的配置来自**上层某个完全不相干的项目**，甚至用户主目录；出了怪结果，但输出里看不到「实际用了哪个根」。
- **根因**：`findProjectRoot(cwd)`（`.tmp/old/plugin/lib/run-eval.ts:275-287`）从 `cwd` 逐级 `dirname` 向上，**只要**命中 `.opencode/` 或 `.claude/` 就立刻返回该目录；不校验 `.opencode` 里是否真有 `skills`、不限制向上层数、不打印实际命中的根；循环到盘符根才结束，未命中时回退 `cwd`。调用侧仍在用它取根：fork 中间态 `.tmp/old/plugin/skill-creator.ts:367`（默认 `projectRoot: () => findProjectRoot()`）与 `:1091`（`findProjectRoot(locationDirectory)`）。
- **实证（Windows）**：`~/.opencode` 是 **opencode 自己的运行时目录**，内含 `source-cache/`、`plugins-cache/`、`plugins-data/`、`plugins-log/`、`skills/`、`node_modules/`、`package.json`——它**不是项目根**。而"命中 `.opencode` 即返回"这条规则对它同样成立：只要工作目录位于 home 之下（临时目录、home 内任意子目录），向上查找就**会命中 `~/.opencode`，把 home 目录当成项目根返回**。这就是「用错项目根」的实证，也解释了为什么本机跑 B2b（迁 `lib/`）的取根用例时，「兜底返回 cwd」这条分支**不可达**（只能 skip）——在 home 之下永远会先命中 `~/.opencode`。
- **后果**：评测镜像的是**错误的项目**——错项目里的兄弟技能、`instructions`、配置一起进 `evalRoot`，触发率反映的不是被测技能在用户项目里的表现；由于不报告命中根，用户只能从「拷贝了多余的东西」这种间接症状推断，排障成本高。注意上游已经修过一半：`runEval` 现在收调用方传入的 `projectRoot`（`RunEvalOptions.projectRoot`，`:852-858`；skill 枚举器同样按传入根工作，`:134-136`），回归测试也明确守住这一点（`.tmp/old/plugin/test/run-loop.test.ts:110-113`：「loop 必须用调用方传入的 instance root，不能用 process-cwd 派生的 root（旧 `findProjectRoot()` 在 loop 顶部就是被这个测试守住的回归）」）。**风险在于壳层仍在两处调用它**。
- **正确做法（已定稿，按优先级执行）**：项目根**只来自调用方传入的上下文**，取值顺序固定：
  1. `ToolContext.directory`（当前会话的项目目录）——**首选**，路径解析一律以它为基准；
  2. 它为空时用 `worktree`（工作树根）；
  3. 两者都没有 → 三段式报错 `错误：拿不到当前项目目录` / `改法：在 opencode 会话内重试，或显式传绝对路径`。

  **禁止 `process.cwd()`、禁止向上查找目录**——上游就是在这一点上把 `~/.opencode` 判成项目根的。向上查找只在「独立 CLI 场景」（进程里拿不到 `ToolContext`）保留为兜底，且必须满足两条：① **排除 opencode 自身的运行时目录**——至少识别 `~/.opencode`（缓存、插件数据、`skills/` 所在的运行时目录）与 `~/.config/opencode`（用户配置目录），命中它们不算命中；② **命中后校验「项目形态」**（含 `.opencode/skills` 或 `opencode.json(c)` 等项目配置）才算数，并把**实际使用的根打印出来**（含来源：调用方传入 / 向上命中 / 回退当前目录）。
- **验收方式**：
  - 单测（分发层，已在 B2 落地：`test/dispatch-context.test.js`）：`ToolContext.directory` 被原样透传并按它解析相对路径；它为空时回退 `worktree`；两者皆空时输出三段式（恰好三行）。
  - 单测（独立 CLI 兜底路径）：临时目录下造 `A/.opencode/skills/...`、`A/B/work/`，以 `A/B/work` 调用兜底取根函数，断言返回 `A` 且日志里**含 `A` 的路径**；断言这条路径只在拿不到 `ToolContext` 时才会走到。
  - 单测：对 `process.cwd` 打桩，断言取根过程**不读**它（证明根不来自进程 cwd）。
  - 单测（实证用例）：从 **home 下的临时目录**（`os.tmpdir()` 派生或 home 内任意子目录）调用兜底取根，**不得**返回 home 目录；若本机存在 `~/.opencode`，断言它被判为运行时目录并跳过，最终结果是「回退当前目录 + 明确提示」，而不是「home」。
  - 单测：候选根只有 `.opencode/` 但没有 `skills` 也没有项目配置时，断言不采纳（打印「不是项目形态」并继续/回退）。

### C 被测技能本体泄漏：合成技能与真身同时在候选集里

- **现象**：通过率莫名其妙偏低，失败用例集中表现为「没触发」；把 `evalRoot` 留下来看，发现里面既有合成技能 `<名字>-skill-xxxx`，也有被测技能的原样目录。
- **根因**：镜像逻辑天生会带 `.opencode/skills/` 下的条目；若不带守卫，被测技能就会以原名重新出现，模型选中真身时合成技能自然是 0 命中。上游已加三道守卫：`referencesSkillsRoot`（canonical 判定是否指向 `.opencode/skills`）、`isWithinExcludedSkill`（被测技能自身）、`isAncestorOfExcludedSkill`（被测技能的祖先目录，禁止整棵拷进来）（`.tmp/old/plugin/lib/run-eval.ts:335-381`，落点 `:656-658`、`:682-687`、`:613-624`）。
- **后果**：假 0（false negative）。这是所有坑里对结论杀伤最大的一个——不是「多拷了东西」，而是**结论方向错了**。
- **正确做法**：**新实现必须原样保留三道守卫**，包括祖先判定（少了它，一个 `references/` 指向被测技能父目录的配置就会把整个 `skills/` 搬回来）；被测技能路径尽量显式传入，未传时按 `<projectRoot>/.opencode/skills/<skillName>` 兜底（`:670` 的做法）。
- **验收方式**：单测在 `.opencode/skills/` 下同时放 `foo`（被测）与 `bar`（兄弟），跑镜像后断言：`evalRoot` 内**不存在** `foo` 的任何路径（按内容哈希判定，不按名字），`bar` 完整存在；再补一条「根配置文档引用 `foo/..`（`foo` 的父目录）」用例，断言父目录整棵未被拷贝，且调试输出点名拒绝了该引用。

### D 符号链接别名绕过守卫：`.opencode/skills` 根自身或祖先被镜像回来

- **现象**：守卫都在，被测技能还是出现在 `evalRoot` 里——只是换了个名字（例如 `skills/alias`）。
- **根因**：守卫若按字符串前缀比较，一个 symlink 就绕过去了。三种典型绕过：① `.opencode/skills/alias -> .opencode/skills`（把整个技能根搬回）；② `.opencode/skills/alias -> <某包含被测技能的父目录>`（祖先别名，整棵子树带回来）；③ `.opencode/` 下某条目的别名指向 `.opencode/skills`（不在 skills 目录里，却指向它）。上游用 canonical 路径解决：`referencesSkillsRoot` 做 realpath 比较（`:335-344`）、`canonicalEntry === canonicalSkillsRoot` 拦根自身（`:678`）、`isAncestorOfExcludedSkill` 拦祖先（`:687`），且守卫失败时**fail closed**（宁可多排除，不放进来）。
- **后果**：同 C，且更难发现——按名字找 `foo` 找不到，实际上内容都在。
- **正确做法**：所有排除判定一律用 canonical（`realpath`）比较，覆盖「相等」「在 skills 根内」「是 skills 根本身」「是被测技能的祖先」四种情形；比较失败（路径不存在、权限错）时按「禁止」处理。
- **验收方式**：单测分别构造上述三种别名（可用 symlink，Windows 上无权限时跳过该用例并**显式报告跳过原因**，不得静默通过），断言 `evalRoot` 中按内容哈希搜索时**不含被测技能的任何文件**；再补一条断言：正常兄弟技能（非别名）仍然被镜像，证明守卫没有误伤。

### E 兄弟技能被一起镜像：设计取舍，不是 bug

- **现象**：评测时把项目里另外若干个技能也搬进了 `evalRoot`，用户觉得「这不是多余的吗」；同时通过率会受兄弟技能强弱影响——项目里再加一个描述极宽泛的技能，被测技能的通过率就掉。
- **根因**：`:662-690` 是**有意**镜像 `.opencode/skills/` 下除被测技能外的兄弟技能的（`:671-689`），目的是让候选集与用户真实项目一致：真实使用中模型确实在同一批技能里挑，只放被测技能会让命中偏乐观（假阳性）。
- **后果**：触发率**更接近真实**，但与项目强耦合：同一技能换个项目跑出不同分数，跨项目不可比；拷贝量与兄弟技能总量成正比（A 的降级分支会放大这一点）。
- **正确做法**：**已定方案 C（2026-10-29）：兄弟技能必须镜像**（见下节「定稿范围」）。理由：评测要预测真实竞争关系，兄弟技能就是候选集的一部分；去掉它们只会让分数虚高（假阳性）。要压制的「多余拷贝」另有病根——A 的整目录 `cpSync(recursive)`，与「该不该镜像兄弟技能」是两回事。同时 A/C/D 的守卫一条都不能少。
- **验收方式**：单测在 `.opencode/skills/` 下放被测技能 `foo` 与两个兄弟 `bar`、`baz`，断言 `evalRoot` 内 `bar`/`baz` 完整存在（逐文件与源一致），被测 `foo` 按内容哈希搜不到；再断言「兄弟技能目录里白名单外的条目（如 `dist/`）」不进去（J1）。

### F 全局同名技能遮挡：不处理就只能先删掉自己的技能才能评测

- **现象**：项目里**没有**同名技能，评测却直接中止，报「skill "X" is already available to opencode at `<路径>`」；用户按提示只能去删已安装的全局技能、或改它的 `skills.paths` 条目——「评测一个已经装在全局的技能」这个最常见的场景反而跑不了。
- **根因**：合成技能的名字是 `<基础名>-skill-<随机 id>`（`.tmp/old/plugin/lib/run-eval.ts:726-736`），评测只把**这个名字**的触发算命中；而**全局技能在 eval 子进程里不会被隔离**——`buildOpencodeEnv` 只覆盖 `PWD`（`.tmp/old/plugin/lib/process.ts:48-50`），不动 `HOME` / `XDG_CONFIG_HOME`，所以装在 `~/.config/opencode/skills`、`~/.claude/skills`、`~/.agents/skills` 的同名技能照样被发现。模型面对两个近乎同名的技能（基础名 vs 合成名），可能选中旧的那个 ⇒ 假阴性。上游的处理是**发现同名就直接中止**：`assertNoInstalledSkillConflict`（`.tmp/old/plugin/lib/run-eval.ts:221-236`，由上游 PR #32 / commit `81efc24` 于 2026-07-05 引入），提示语要求「Remove that installed skill or its skills.paths entry before running skill_eval」（`:210-215`）；调用点在评测与优化入口（fork 中间态 `.tmp/old/plugin/skill-creator.ts:607`、`:753`）。
- **后果**：把「处理用户环境」的成本转嫁给用户，而且是**不可逆**的那种（删自己装好的技能）；用户绕过的现实做法是给技能临时改名或临时移出目录，跑完再改回来——容易忘、也容易污染用户的技能库。注意 `PWD` 隔离已经修过（`process.ts:40-46` 注明源自 PR #42），但那只解决「项目根跑偏」，解决不了「全局同名技能仍在候选集里」。
- **正确做法**：**不改用户任何目录，改 `evalRoot`**。在 `evalRoot/.opencode/opencode.json` 里写 `{ "permission": { "skill": { "<基础名>": "deny" } } }`，把旧技能在**本次评测的子进程内**屏蔽掉。依据：`permission.skill` 的类型是 `PermissionRuleConfig`（opencode v1.18.25 `packages/sdk/js/src/v2/gen/types.gen.ts:1682`），可用技能列表按 `PermissionV2.evaluate("skill", name, …)` 过滤掉 deny 项（`packages/core/src/skill.ts:30-31`；`packages/opencode/src/skill/index.ts:314` 同理），被 deny 的技能不进 `available_skills`，模型只能在合成技能（及方案 C 的兄弟技能）里挑。deny 不生效（老版本不支持按名 deny）时**回退成冲突中止**——保持上游的「宁可停也不给错结果」，并把「实际路径 + 可直接复制的处置命令」打进错误三段式。确实需要「旧技能在场」的对照实验时，用 `--no-shadow-guard` 显式关闭自动屏蔽，行为回到「检测到冲突即中止」。
- **验收方式**：
  - 单测（deny 生效）：探测目录放同名技能 `demo` 后跑评测，断言 `evalRoot/.opencode/opencode.json` 里 `permission.skill.demo === "deny"`；同用例断言**源目录文件集合与哈希前后一致**（证明没写用户目录）。
  - 单测（兜底）：把配置写入打桩成失败（或声明目标版本不支持按名 deny），断言不进入执行阶段，且错误三段式的「改法」里含**实际路径**与一条可复制命令。
  - 单测（开关）：加 `--no-shadow-guard` 后，断言**未写任何 deny 配置**，且命中同名技能时中止（回到上游行为）。

## 方案对比（**已选 C，2026-10-29**）

| 方案 | `evalRoot` 内容 | 优点 | 代价 |
|---|---|---|---|
| A 只放被测技能 | `evalRoot/.opencode/skills/<cleanName>/SKILL.md` + 最小可行配置（`opencode` 能起来即可，不镜像源项目配置） | 最干净：多余拷贝趋近 0，跑得快、成本低、结论可复现。触发率**可不可信**：只对「技能本身写得怎么样」可信，对「在用户项目里能不能竞争过别的技能」不可信，偏乐观 | 与**真实环境差异最大**：没有项目配置、没有兄弟技能、没有 `instructions`，模型看到的候选集与线上不同；通过率高不等于线上高，适合做 description 的 A/B 对比，不适合对外报绝对分数 |
| B 被测技能 + 配置，不放兄弟技能 | 合成技能 + `.opencode/`（除 skills）+ 根配置文档及其相对引用 | 保留项目上下文，`instructions`/配置类行为与真实一致；多余拷贝少（配置面通常很小）；结论**可复现**且不受别人技能影响 | 与**真实环境差异居中**：候选集缺了兄弟技能，命中偏乐观（假阳性）；触发率**部分可信**（相对排序可信，绝对值偏高）；用户会问「为什么线上没触发」 |
| **C 保留上游语义：兄弟技能 + 配置，只修掉整目录递归拷贝 ← 已选（2026-10-29）** | 合成技能 + `.opencode/`（除 skills）+ 根配置文档及引用 + **兄弟技能** | 与真实环境**最接近**，候选集与线上一致，触发率**可信任度最高**（能反映竞争关系） | **仍会有「多余拷贝」**（兄弟技能逐个镜像，A 的降级分支会把每个技能目录的真身拷一遍）；结论与项目强耦合、跨项目不可比；实现与测试面最大（要守住 C/D 的守卫） |

三条判据单独对照：

| 判据 | A 只放被测技能 | B 技能 + 配置 | **C 上游语义 + 修拷贝（已选）** |
|---|---|---|---|
| 触发率可不可信 | 偏乐观；只可横向比同一技能的不同 description | 偏乐观；相对排序可信 | **最可信**；绝对值与竞争关系都可参考 |
| 是否会出现多余拷贝 | 几乎不会 | 少（仅配置面 + 引用的相对文件） | 会（兄弟技能全量镜像）——但**只允许逐条目/逐文件**，禁整目录递归拷贝 |
| 与真实环境差异 | 最大 | 中 | **最小** |

### 决策记录（2026-10-29）

- **原来**：三案并列、尚未拍板（A 只放被测技能 / B 技能 + 配置 / C 上游语义）。
- **现在**：**选 C**——镜像范围 = 合成技能 + 项目根 `opencode.json(c)` 及其引用文件 + `.opencode/` 除 `skills` 外全部条目 + `.opencode/skills` 下除被测技能外的兄弟技能。
- **理由**：
  1. 评测的价值在于**预测真实竞争**：真实使用中模型面对的是「本项目全部技能」这个候选集，兄弟技能参与竞争，去掉它们只会让分数虚高（假阳性），结论不可用于判断「装进项目后会不会被触发」。
  2. 「拷多余的东西」的病根在 **A（整目录 `cpSync(recursive)`）**，不在镜像语义本身——修掉递归拷贝后，镜像兄弟技能是逐条目可控的，不存在失控体积。
  3. 同名遮挡这一历史包袱（坑 F）已由「在隔离根写 `permission.skill.<基础名> = "deny"`」解决，**与选哪个方案正交**；不再需要为「怕撞名」而砍掉兄弟技能。
  4. A/B 的「环境精简」收益可事后补：需要做 description 的 A/B 对比时，把项目里的兄弟技能临时移出即可，不需要在实现里做两套镜像模式。
- **代价与对策**：结论与项目强耦合（跨项目不可比）——输出里注明本次镜像的兄弟技能数量与名称；兄弟技能镜像走 J1 的逐条目 + 大小上限，且保留 C/D 守卫。

### 定稿范围（J9）

**必需镜像**（少一条都算评测失真）：

1. **合成技能本体**：`evalRoot/.opencode/skills/<基础名>-skill-<id>/SKILL.md`（本次评测生成）。
2. **项目根配置文档及其引用文件**：`opencode.json` / `opencode.jsonc`，以及它们 `instructions` / `{file:…}` 引用的相对文件——**丢了会丢 provider / agent / model 配置与项目指令，评测直接失真**。
3. **`.opencode/` 下除 `skills` 外的全部条目**（配置、agent、command、plugin 等）：同样属于「丢了就失真」的配置面。
4. **`.opencode/skills/` 下除被测技能外的兄弟技能**（方案 C）。

**禁止进入**：被测技能本体、其祖先目录、`skills` 根自身、指向 skills 的别名（C/D 守卫）。

**方式**：逐条目 / 逐文件 + 单文件大小上限；禁止对任何目录做 `cpSync(..., { recursive: true })`；`symlinkSync` 成功时保持零拷贝。

> C **不等于**保持现状：C 必须同时把 A（降级路径不递归）与 B（根来源受限）修掉，否则「最接近真实」会被「拷错项目」抵消。

坑 F（全局同名技能遮挡）与镜像范围**正交**：它问的是「已经装在别的目录、根本不在镜像范围内的同名技能怎么不进候选集」，与「`evalRoot` 里放哪些东西」互不影响。方案 C 也一样要处理 F——C 不动 `HOME` / `XDG_CONFIG_HOME`，全局技能照样可见。

## 对实现的约束（J1–J9，可直接转测试点）

**J1 拒绝整目录递归拷贝**
- 要求：任何镜像/拷贝路径都不得对未知条目做 `recursive` 拷贝。symlink 失败时降级为**逐文件拷贝已知条目**（配置文档白名单、配置文档引用的相对文件、技能目录白名单 `SKILL.md` / `agents/**` / `references/**` / `templates/**`），其余跳过；单文件大小上限提为常量，超限跳过。**禁止**对任何目录调用 `cpSync(..., { recursive: true })`。
- 判定：打桩 `symlinkSync` 抛 `EPERM` 后跑镜像；断言目标文件集合 ⊆ 已知条目集合；断言含 `node_modules/`、`dist/`、`.git/` 的源目录未进入 `evalRoot`；断言超限文件未拷贝；**源码门禁**：对 `src/lib/` 做 `grep -n "cpSync(.*recursive"`，命中数必须为 0（整目录递归拷贝不存在）。

**J2 项目根只来自调用方传入的上下文（优先级 `directory` → `worktree` → 报错）**
- 要求：`eval`/`optimize` 的项目根**只**取自调用方传入的上下文——先 `ToolContext.directory`，为空用 `worktree`，两者都空则三段式报错（`错误：拿不到当前项目目录`）。**禁止 `process.cwd()`、禁止向上查找**。向上查找只在「独立 CLI 场景」（无 `ToolContext`）作为兜底，且必须 ① 排除 opencode 自身运行时目录（`~/.opencode`、`~/.config/opencode`，命中不算命中）；② 校验项目形态（含 `.opencode/skills` 或 `opencode.json(c)`）；③ 输出实际命中的根（含来源）。
- 判定：单测断言 `directory` 被原样使用、`worktree` 为次选、两者皆空时输出三段式（恰好三行）；`process.cwd` 打桩后取根过程不读它；源码门禁：`src/cli/**` 与 `src/tool.ts` 内 `process.cwd()` 真实调用数 = 0（注释提及不算）；兜底路径另测：**从 home 下的临时目录调用时不得返回 home 目录**（存在 `~/.opencode` 时判为运行时目录跳过）、只有 `.opencode/` 而无 `skills`/项目配置的候选根不被采纳。

**J3 被测技能本体与其祖先目录永不进入 `evalRoot`**
- 要求：保留三道守卫（`referencesSkillsRoot` / `isWithinExcludedSkill` / `isAncestorOfExcludedSkill`）的语义，含 canonical（`realpath`）比较与 fail-closed；被测技能路径显式传入，缺省按 `<projectRoot>/.opencode/skills/<skillName>` 兜底。
- 判定：被测技能与兄弟技能同存时，`evalRoot` 内按内容哈希搜不到被测技能；祖先目录整棵不被拷贝；别名（skills 根自身、祖先、`.opencode/` 下指向 skills 的条目）三种用例均被拒，且正常兄弟技能仍被镜像。

**J4 `evalRoot` 清理必须在 `finally` 级**
- 要求：正常结束、抛错、取消（`AbortSignal`）三条路径都删除 `evalRoot`；`rmSync` 失败不得掩盖原始错误（最多追加一条提示）；预取消时不得创建 `evalRoot`。
- 判定：三个用例（成功 / 抛错 / 取消）结束后断言临时根目录不存在；`rmSync` 打桩抛错时断言原始错误仍按三段式返回；预取消用例断言从未调用 `mkdtempSync`。

**J5 镜像清单可打印**
- 要求：`SKILL_ZH_DEBUG=1` 时输出镜像清单——每个被镜像条目的相对路径、类型（symlink / file / dir）、字节数，以及被跳过的条目与跳过原因；默认（未开调试）只输出一行汇总（条目数与总字节数）。
- 判定：调试模式下对清单做快照比对（条目集合 + 大小），断言与磁盘实际内容一致；未开调试时断言输出不含逐条清单。

**J6 eval 前自动屏蔽同名技能（不改用户目录）**
- 要求：执行前先枚举「当前可见技能」；命中与被测技能**基础名**相同的条目时，在 `evalRoot/.opencode/opencode.json` 写入 `permission.skill.<基础名> = "deny"`，使旧技能在该子进程内不可见；**不得**修改、移动、删除用户的任何技能目录或配置，也不得要求用户先手动作业。
- 判定：探测目录放同名技能后跑评测，断言 `evalRoot` 配置文件里 `permission.skill.<name> === "deny"`；断言探测目录文件集合与内容哈希前后一致；断言输出里不出现「先删除/先改名」这类前置要求。

**J7 deny 写不进或版本不支持时回退冲突中止**
- 要求：deny 配置写入失败、或目标版本不支持按名 deny（写进去也不生效）时，**不进入执行阶段**，按三段式返回失败，且「改法」里含冲突的实际路径与一条可直接复制的处置命令；不得静默放行去跑（那会把遮挡算成假阴性）。
- 判定：把配置写入打桩成抛错，断言未 spawn `opencode run`、错误三行完整且含实际路径与可复制命令；用「不支持按名 deny」的假版本跑同一用例，断言行为一致。

**J8 `--no-shadow-guard` 关闭自动屏蔽**
- 要求：`--no-shadow-guard` 时不写任何 deny 配置，行为回到「检测到同名冲突即中止」；该开关只影响屏蔽行为，不影响 J1–J5。
- 判定：加 `--no-shadow-guard` 且存在同名技能时，断言 `evalRoot` 内无 deny 配置、且以冲突消息中止；无同名技能时断言评测正常执行。

**J9 镜像范围固定为方案 C（四项缺一不可）**
- 要求：`evalRoot` 必须且只能由下列四项构成——① 合成技能本体（`<基础名>-skill-<id>/SKILL.md`，本次生成）；② 项目根 `opencode.json` / `opencode.jsonc` **及其引用文件**；③ `.opencode/` 下**除 `skills` 外的全部条目**；④ `.opencode/skills/` 下**除被测技能外的兄弟技能**。②③ 是必需镜像：丢了会丢 provider / agent / model 配置与项目指令，评测失真；④ 是方案 C 的核心，丢掉只会让分数虚高。禁止选项：被测技能本体、其祖先、`skills` 根、指向 skills 的别名（C/D 守卫）。
- 判定：单测造「根配置 + `.opencode/` 含 agent/command 条目 + `skills/` 含兄弟与被测」，跑镜像后按相对路径快照断言：配置文件与其引用文件存在、`.opencode/` 非 skills 条目存在、兄弟技能存在、被测技能按内容哈希不存在；再断言 `evalRoot` 内**不存在**四项之外的顶层条目（白名单外不放行）。
