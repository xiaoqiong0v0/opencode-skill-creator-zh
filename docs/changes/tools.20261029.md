# tools.md 变更说明（2026-10-29）

## `eval` 一节新增「隔离根与镜像范围」

**原来**：`eval` 一节只写参数、评测集格式、输出示例与两类失败示例；对「评测在哪个目录跑、那个目录里放了什么」完全不提。用户只能在跑完后发现临时目录里多出东西，或者发现分数不对劲却无从判断原因。

**现在**：在 `eval` 与 `optimize` 之间新增小节「隔离根与镜像范围」：说明为什么需要隔离根（否则 `opencode` 按 `$PWD` 加载项目里同名的真实技能，结果恒为 0）；用一张三方案表（A 只放被测技能 / B 加配置 / C 加兄弟技能）列出各方案对分数的影响（当时方案未定，故并列三案）；再列三条硬约束（不整目录递归拷贝、项目根不靠向上找且要写明实际根、被测技能本体与祖先不泄漏），并说明 `SKILL_ZH_DEBUG=1` 可打印镜像清单、临时根在结束时删除。

**为什么**：隔离根的内容直接决定触发率的含义，属于用户会依赖的行为口径（「我看到的通过率代表什么」），必须写进子命令参考而不是只留在设计文档里；当时方案未定，写死具体行为会误导用户，所以只写约束、并列三种范围（已于同日后批定稿为 C，见下）。细节见 [../design/技能评测隔离问题.md](../design/技能评测隔离问题.md)、需求口径见 [SPEC 的 `R6.2`](../SPEC.md#r62-技能评测隔离约束)。

## `eval` 补「同名技能遮挡与自动 deny」与 `--no-shadow-guard`（同日第二批）

**原来**：`eval` 的参数表只有技能目录、`--runs`、`--workers`；「同名技能在场会怎样」完全没写。用户跑评测时莫名中止，只能按英文提示删掉自己装好的技能。

**现在**：参数表加 `--no-shadow-guard`；新增「同名技能遮挡与自动 deny」小节：说明合成技能只认 `<基础名>-skill-<id>`、全局技能不随 `PWD` 隔离，本版改为在隔离根的 `.opencode/opencode.json` 写 `permission.skill.<基础名> = "deny"`（不动用户目录）；用一张三行表写清「发现同名 → 自动 deny 继续跑」「deny 写不进或版本不支持 → 三段式中止并给可复制命令」「加 `--no-shadow-guard` → 不写 deny、检测到即中止」。

**为什么**：`--no-shadow-guard` 是用户可见参数、自动屏蔽会改变评测语义（旧技能被临时隐藏），两者都必须写进子命令参考；同时明确「只在临时隔离根内生效、不读写用户技能目录」，避免用户担心被动过配置。约束口径见 [SPEC 的 `R6.2`](../SPEC.md#r62-技能评测隔离约束) 的 J6–J8。

## `eval` 的镜像范围定稿为方案 C（同日第三批）

**原来**：「隔离根与镜像范围」一节把 A / B / C 三种范围并列，方案未定；用户看不出「我跑一次到底会镜像什么」，也无法判断分数能不能代表真实使用。

**现在**：小节标题去掉悬置标注，正文写死方案 C 的四项范围——① 合成技能本体；② 项目根 `opencode.json(c)` 及其引用文件；③ `.opencode/` 除 `skills` 外全部条目；④ `.opencode/skills/` 下除被测技能外的兄弟技能；列明「不镜像」清单（被测本体、祖先、`skills` 根、指向 skills 的别名、`src/`/`dist/`/`node_modules/`/`.git/`），并把硬约束扩到 J1/J2/J3/J9；补一句方案 C 的取舍（与项目强耦合、跨项目不可比、做 A/B 对比时可先把兄弟技能移出）。

**为什么**：用户已定方案 C。写死范围后，本条从「设计取舍」变成可依赖的行为约定（用户能据此判断「我的 0.85 代表什么」）；同时点明「拷多余的病根在递归拷贝而非镜像语义」，避免把方案 C 误读成「恢复上游整目录拷贝」。细节见 [../design/技能评测隔离问题.md](../design/技能评测隔离问题.md)。

## 新增「路径解析基准」一节，旧口径改正（同日第四批）

**原来**：`## 通用约定` 的「路径基准」一行写「相对路径按 OpenCode 进程的工作目录解析」——这正是坑 B 的错误口径（进程 cwd 不等于会话项目目录）；全文也没有「技能可以写在任意目录」的说明。

**现在**：新增 `## 路径解析基准` 小节，写四种情形（相对路径按 `ToolContext.directory`、为空用 `worktree`；绝对路径原样；两者都空走三段式 `错误：拿不到当前项目目录`；路径不存在走三段式），并补两条硬口径——① 不用 `process.cwd()`、不向上查找（仅独立 CLI 场景兜底，且排除 `~/.opencode` / `~/.config/opencode`）；② 技能可写在任意目录，只要路径给对。通用约定的「路径基准」行改为指向新小节；`eval` 的 J2 硬约束同步；开头状态行改为「B0/B1 完成、B2 单工具壳已落地」。

**为什么**：路径基准决定用户能不能照着示例直接跑通，写错一次就是「文件找不到」；而上游的 cwd 向上找正是「评测镜像了错项目」的根因，必须在用户能读到的地方写死禁止项。

## `help` 覆盖 7 个子命令，`install` 一节标注当前状态（同日第五批）

**原来**：`skill_zh help` 一节写「打印完整用法：6 个子命令说明」；`skill_zh install` 一节写「`skill_zh help` 与『未知子命令』的可用列表仍只列 6 个，本节为目标行为」。

**现在**：「6 个子命令说明」改为 7；`install` 一节改为「`help` 与『未知子命令』的可用列表已含 `install`（B2 落地），但调用 `skill_zh install` 目前返回『尚未实现』三段式；参数与输出仍为目标行为」。参数表、示例与失败示例不变。

**为什么**：`help` 与可用列表已经含 `install`，若文档还说「只列 6 个」，用户按文档判断就会以为命令不存在；把「已列但未实现」写清楚，才能让人知道现在能做什么、B5 之后能做什么。

## `new` / `validate` 两节按实际实现重写（同日第六批）

**原来**：`new` 一节写 `--dir` 默认 `./skills`、`--force` 覆盖「已生成文件」、输出里 `references/` 只有一行占位；`validate` 一节的输出示例含 `frontmatter` / `references/ 3 个文件` 两行，失败示例直接是三段式 `错误：description 超长…`。

**现在**：`new` 写实际口径——技能名必须匹配 `^[a-z0-9]+(-[a-z0-9]+)*$` 且 ≤ 64 字符、`--dir` 缺省为**当前会话项目目录**、目标目录存在且**非空**才拒绝、`--force` 只重写 `SKILL.md` 与 `references/示例.md` 并把旧 `SKILL.md` 备份成 `.bak`；输出示例换成真实生成清单，失败示例按实际文案补「目标已存在」与「技能名不合法」两条。`validate` 写实际结论口径（`通过` / `未通过（N 处问题）`、每条含 `问题` + `文件:行` + `改法`、通过时给 description 字符数），补「缺省只提示、`--strict` 判失败」的两份对照输出与「目录名与 name 不一致」示例；路径不存在的改法按显示路径给出（`--dir ./skills`）。开头状态行同步为「B3 已接真实现，new/validate 可用；eval/optimize/package 待 B4、install 待 B5」。

**为什么**：这两节此前写的是目标行为，用户照着 `--dir` 默认值或 `--force` 语义写脚本会踩空；`--strict` 会让同一个目录的结论从「通过」翻成「未通过」，必须把两份输出都摆出来，用户才能判断什么时候用、怎样算达标。

## 复核修正：`validate` 报全问题、调试入口改正、可用列表补 `install`（同日第九批）

**原来**：`validate` 只报 `validateSkill` 的第一条问题，且判失败时把提示吞掉（用户要先修完错误再跑一次才看见）；结论文案是 `未通过（N 处问题）`，不区分错误与提示；通用约定的「调试」行写 `SKILL_ZH_DEBUG=1`「B3 落地」（实际未实现）；未知子命令示例的可用列表漏了 `install`；`new` 的 `--force` 只说备份旧 `SKILL.md`。

**现在**：`validate` 一次报全（未知键、未引号非法取值、缺 name/description、name 规范、description 长度、兼容性超长各自成条），错误与提示分开计数并**一并输出**（`未通过（2 处错误，1 处提示）` / `[错误 n]` / `[提示 n]`），补一份「同时有错误与提示」的示例；路径不存在时，目录名不是 kebab-case 就改给「先按 kebab-case 改目录名，或 `skill_zh new my-skill`」；「调试」行改为 `SKILL_ZH_DEBUG=1` 尚未实现、现有入口是 `SKILL_ZH_LOG_DISABLE=1` 与 `plugin-logger.jsonc` 的 `enabled`；示例可用列表补 `install`；`--force` 改为两个被覆盖文件各留 `.bak` 并在输出点名。

**为什么**：只报第一条会让用户「修一条、跑一次」，且失败时看不到提示等于提示白写；文档写着一个不存在的调试开关，会让排查的人白试一轮；可用列表漏 `install` 会让用户以为命令不存在。

## eval / optimize 两节按实际实现重写（同日第十批）

**原来**：eval 只列 `<技能目录>` / `--runs` / `--workers` / `--no-shadow-guard`，默认值写「见实现常量」，评测集默认写 `evals/evals.json`；optimize 只列 `<技能目录>` / `--iterations`；没有 `--timeout` / `--model` / `--agent` / `--eval-set` / `--log-dir`，也没有报告落盘说明；通用约定里 `SKILL_ZH_DEBUG=1` 标「尚未实现」。

**现在**：两节按落地实现重写——eval 九个选项全部列出（默认 1/1/120000ms/opencode 默认/build、评测集 `<技能目录>/eval_set.json`、报告目录 `<技能目录>/.evals`）；optimize 八个选项与 6:4 切分、HTML/JSON 产物；补评测集格式、真实输出示例（逐条结果、失败分组、镜像汇总、报告路径）、缺参/评测集缺失/非法参数/deny 写入失败的失败示例；隔离根与 deny 两节按 J1–J9 更新（2 MiB 上限、逐文件降级、`SKILL_ZH_DEBUG=1` 清单、deny 合并与摘链、J7 回退）；通用约定与状态行同步为「B0–B4 完成 / eval、optimize 可用」。

**为什么**：默认值写「见实现常量」等于让用户去读源码；评测集默认名与实现不一致会直接导致「按文档放文件却报缺失」；缺 `--timeout` / `--agent` 会让用户以为不支持。文档必须能独立支撑「照着敲一条命令」。

## B4 复核修复：optimize 产物目录、`--log-dir` 与示例对齐（同日第十一批）

**原来**：optimize 的实时报告与改善记录固定叫 `optimize-report.html` / `improve_iter_<n>.json`，两次运行会互相覆盖，文档也写成单层目录；optimize 的 `--log-dir` 实际生效但选项表未列；镜像示例写「共 0.1 KB」，而符号链接镜像的字节数为 0（实际输出是「链接镜像」）；deny 小节写「你的技能目录与全局配置不会被读写」，把报告落盘这条唯一写入点说过头了。

**现在**：optimize 每次运行落独立子目录 `<logDir>/optimize-<时间戳>-<随机>/`，文档补目录结构表（HTML / JSON / `improve_iter_<n>.json`）与 `--log-dir` 选项；镜像示例改成实际输出「链接镜像」；deny 小节限定为「deny 配置不读写用户其它技能目录与全局配置；报告默认写 `<技能目录>/.evals`（可用 `--log-dir` 改）」。

**为什么**：固定文件名在同一技能上跑两次 optimize 就会覆盖上一轮证据，排查时无法对比；文档没列 `--log-dir` 等于把一个已支持的选项藏起来；示例与真实输出不一致会让用户以为镜像坏了。

## package / install 改为实际行为

**原来**：`package` 只写目标行为（导出后自检），`install` 整节标「B5 实现」且没有 `--dir`；输出示例是按规划写的，与实现不一致。

**现在**：两节都改成实际行为——`package` 补 `--out` 必填、导出到源目录内部 / 目标非空 / 结构不合规的失败示例、白名单外跳过清单、文件字节数；`install` 补 `--dir`、启动钩子行为、状态文件路径、冲突探测与 5 类处置动作、`--force` 备份位置、幂等与失败示例，并注明 `SKILL_ZH_SKILL_SOURCE` / `SKILL_ZH_NO_STARTUP_INSTALL` 两个排障开关。

**为什么**：文档里的命令与输出必须能照抄执行；保留「B5 实现」标记会让模型误以为仍会返回「尚未实现」。

## B5 复核：package / install 口径补齐

**原来**：`package` 只拒绝「导出到源内部」，`--out` 是源祖先时会被当成普通空目录写入；`install` 的 `--dir` 没写空值与 `~` 规则，冲突探测写成项目单层，`--dry-run` 的清理 / 删除 / 备份仍用完成态措辞。

**现在**：`package` 补「祖先目录」拒绝与 realpath（最近存在祖先）比较；`install` 补 `--dir` 空值报错、`~` 展开、项目目录逐层 / 任意层级 / frontmatter name 探测、`--dry-run` 全部改「将…」措辞；旧版 `SKILL.md.user-backup` 仅在内容等于当前或包内版本时清理，否则迁到状态目录并点名。

**为什么**：这些是复核发现的绕过与误导点；文档必须与实现一致，照抄输出不会误判「已经写盘」。
